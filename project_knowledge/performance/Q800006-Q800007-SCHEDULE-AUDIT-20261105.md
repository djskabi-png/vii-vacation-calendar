# Q800006 / Q800007 operational audit

Date: 2026-11-05

## Q800006: catalog-sync freshness

### Verified current source

- `vite.config.ts` declares one Worker cron: `*/10 * * * *`.
- `worker/index.ts` invokes `runSupplierCatalogScheduleTick` from the scheduled
  handler and also starts the quality runner, capability refresh and discovery
  warmers in bounded `waitUntil` tasks.
- `app/lib/supplier-catalog-schedule.ts` has four worlds and three daily slots:
  vacations/events/rooms/spa at 05:00/05:30/06:00/06:30, again at
  12:00/12:30/13:00/13:30, and again at 17:00/17:30/18:00/18:30 Israel time.
- The runner derives the due world from the exact Israel-local hour/minute and
  creates a fenced scheduled run ID. A ten-minute cron can reach every listed
  half-hour slot.

### Causal gap

The repository contains configuration and a handler, but no verified live
Cloudflare trigger inventory or successful terminal scheduled run evidence in
the inspected release evidence. The current Cloudflare operations record
explicitly marks scheduled execution as unverified. Therefore a 24-hour stale
catalog cannot be attributed to the supplier, D1, or the schedule algorithm
from this repository alone. The strongest operational hypothesis is that the
managed Site deployment is not running the declared scheduled handler, or its
scheduled invocation lacks the production D1 binding and fails closed at
`scheduled_database_unavailable`.

### Correct repair proposal

1. In the owning Sites/Cloudflare deployment, verify that the deployed Worker
   has the `*/10 * * * *` trigger, `DB` D1 binding and the exact deployed source.
2. Run one read-only scheduled invocation or inspect the scheduler log for each
   world, recording run ID, terminal status, accepted generation and error
   code. Do not manually refresh a catalog as a substitute.
3. Add an authenticated operational view/alert for age of the latest accepted
   generation per world and last scheduled terminal outcome. Alert before the
   24-hour hard freshness boundary.

No sync, catalog write, binding change or deployment was performed in this
 audit.

## Q800007: growth checks

### Verified current source

`app/admin/growth/page.tsx` is a read-only dashboard. It fetches
`/api/admin/overview`, `/api/admin/sitemap` and `/robots.txt` when the page is
opened. It does not schedule or persist growth checks.

The scheduled Worker runs `runQualityChecks`, whose registry contains SEO,
sitemap, catalog, world and place checks with cadence values. It has no
separate `growth` check family or a dedicated growth refresh job. Quality
results are written to the quality tables only when the scheduled handler or a
manual run actually executes.

### Causal gap

The “growth checks pending” state is therefore not evidence of a failed SEO
calculation. It means the dashboard has no fresh quality/overview evidence, or
the scheduled quality runner has not executed successfully. The source cannot
prove which without current D1 `quality_runs` rows and deployed scheduler
logs. The growth page’s static integration copy also describes historical
verification, not a live connector check.

### Correct repair proposal

1. Verify a recent `quality_runs` row with `trigger_kind='scheduled'`, terminal
   status and the expected SEO/catalog check results.
2. Expose the latest run age and outcome in the admin dashboard, separating
   “not run”, “running”, “failed” and “passed”.
3. Keep growth metrics read-only and source them from the authenticated
   overview/search analytics tables. Do not invent a growth score when the
   scheduled run or measurement source is unavailable.

## Verdict

Both items are operational-verification gaps, not safely repairable by changing
the public site or manually running sync. The source schedule is present and
the target slots cover all four worlds, but live trigger, D1 binding and
successful terminal-run evidence remain unverified. Production readiness for
Q800006 and Q800007 is therefore **not verified**.
